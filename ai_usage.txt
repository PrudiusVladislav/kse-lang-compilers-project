   One thing first: practice 4 has no control flow. The handout says outright "no
   branches yet — those are next week". This week is types, comparisons and a
   separate semantic pass. I still answer the loop question below, but it isn't
   part of this practice's grading.

   The tasks

   Task 1 (0.5 pt): three types in the front end. This touches the lexer, grammar
   and Parser.
   - Lexer: new keywords i64, bool, true, false. These go through the same
     KEYWORDS lookup, plus new CATEGORIES entries.
   - Lexer: two new states after = and after !, each accepting only one more =. A
     lone = or ! is a lexical error at that byte.
   - Grammar: type ::= i32 | i64 | bool. The old expr is renamed arith, and the
     new expr ::= arith [ (== | !=) arith ]. factor gains true/false.
   - Parser: parse_statement dispatches on all three type keywords. DeclNode
     carries type_name, and there is a new BoolNode. BinOpNode.op can now be ==
     or !=.
   - Parser: a second comparison is left over after the expression, so it falls
     into the existing "unexpected … after the statement" or "expected '}'"
     paths.
   - Dump: Decl x i32 const. The 4 existing .ast files change only on their Decl
     lines.

   Task 2 (1.5 pt): the semantic pass. This touches a new SemanticChecker class
   and CodeGen, which loses code.
   - The checker walks the whole tree before CodeGen is created. Its symbol table
     maps name → DeclNode.
   - Every expression visit returns a type string and stores it in node.type.
     VarNode and AssignNode get node.decl.
   - The three existing checks move here with the same messages and positions.
     Grading gives 0 for any check that still runs in CodeGen.
   - New rules:
     - A constant gets the narrowest type it fits (i32, then i64, otherwise an
       error).
     - Arithmetic works on integers only and gives the wider type.
     - ==/!= compare two integers or two bools.
     - The only allowed conversion is i32 → i64.
     - Each error has its handout-specified position: at the operator, at the
       name, or at the constant.

   Task 3 (1 pt): typed codegen. This touches CodeGen and the tests.

     checker gave them.
   - A coerce(value, have, want) helper is called at five sites: initialiser,
     assignment, both operands of + - *, both operands of == !=, and the exit
     value.
   - exit of an integer widens to i64 and prints with %lld. exit of a bool uses
     select to pick between the strings true and false.
   - At least 6 ok and 6 err tests, covering the handout's list. All practice 2/3
     tests must still pass.

   The structural change

   Checking moves out of the code generator into its own pass, and the tree
   becomes the contract between the two. The current code can't just absorb this,
   for three reasons:

   1. The symbol table stores LLVM objects. CodeGen.symbols maps a name to
      Var(slot, …), and a slot is an alloca. That can't exist before IR does. The
      checker needs a table from names to declarations that exists before any
      builder does. So Var gets split: the type and mut stay on DeclNode, and the
      slot becomes CodeGen-only.
   2. One visit can't return two things. CodeGen's visits return ir.Values, while
      the checker's visits return types. With types in the language, emitting a
      + b depends on facts about both operands, and emitting an assignment
      depends on the target's declared type. Doing both in one walk means
      returning (value, type) pairs everywhere, which mixes decisions with
      emission. That mix is exactly what the handout grades against.
   3. Errors happen halfway through building the IR. Today a bad line 5 is found
      after lines 1–4 are already in the module. It's harmless now, since nothing
      gets written, but it's why the handout wants the pass to be testable
      without LLVM at all.

   So there's a new phase between parse and walk. The tree gains the type and
   decl fields, and CodeGen goes back to doing lookups only through node.decl.

   Control flow at the IR level (next week, not this one)

   Builder calls involved:
   - Blocks: function.append_basic_block(name) to create them, then
     builder.position_at_end(block) or builder.goto_block to move the insertion
     point.
   - Terminators: builder.branch(target) for an unconditional jump, and
     builder.cbranch(cond_i1, then_block, else_block) for a conditional one.
   - The condition: builder.icmp_signed(op, a, b), which returns an i1.
   - Optional: builder.phi plus add_incoming to merge values without going
     through memory, and builder.if_then / builder.if_else context managers for
     if.
   - Useful checks: builder.block and block.is_terminated. Every block must end
     in exactly one terminator.

   A while loop is four blocks:

   entry ──br──▶ cond ──cbranch(true)──▶ body ──br──▶ cond   (back edge)
                     └──cbranch(false)─▶ after

   - cond loads the variables, runs icmp and ends in cbranch.
   - body ends with an unconditional branch back to cond.
   - Code after the loop continues in after.
   - Variables in alloca slots carry values across the back edge without any phi,
     which is why the existing slot model extends cleanly.

   The only part of this used this week is icmp_signed for ==/!=. The bool exit
   uses builder.select, not branches.

   Three choices the handout leaves open

   1. How a widening is recorded.
   - (a) An explicit Widen/Cast node that the checker inserts into the tree. The
     IR follows the tree exactly, and a missed sext is impossible by
     construction. The costs: the checker rewrites the tree it walks, and --ast
     either shows the node or has to hide it.
   - (b) Leave the tree alone and call coerce(value, have, want) at the five
     sites. CodeGen works out want from sibling types or node.decl.type_name.
     This is what the handout sketches and keeps the tree simple. The cost: the
     widening logic lives in five call sites, and forgetting one only breaks for
     values above 2³¹.

   2. How far the "constant does not fit in i32" message reaches. The handout
   reports i32 x{3000000000} at the constant, not at the name.
   - Bare constants only: i32 x{a + 3000000000} falls back to the generic "cannot
     initialise 'x'…" at the name. Simple, and consistent with the widening
     rule.
   - Any constant that makes the result i64: more precise, but the checker needs
     special-case logic, and it's unclear what to report when two causes combine
     (an i64 variable and a big constant).
   - Also for assignments: extend the same special case to assignments, not just
     initialisers.

   3. The symbol table's shape.
   - Flat dict (the handout's skeleton): the least code now. But the handout
     closes with "the next practice adds blocks, and a block is first of all a
     scope in this pass", so it will be rewritten next week.
   - A stack of dicts now: future-proof, but it's untested code this week, since
     nothing pushes a scope yet.
