  2. Coupling points to cut

  1. Tuples carry tokens; nodes carry line/col. ("const", int, token) and
     ("decl", name_token, …) store the Token object and the walk reaches through
     it (token.line, name.text). The handout is explicit: "The tree holds
     names, numbers, flags and child nodes — never a token." So every
     constructor takes (line, col, …) and the walk's CompileError(...) calls
     read node.line, node.col.
  2. evaluate/load are closures over builder and symbols. They're defined inside
     build() precisely so they can call builder.add without threading state.
     Codegen becomes a CodeGen class (or codegen(builder, symbols) per node)
     with self.builder, self.symbols, self.printf, self.fmt as fields.
  3. load() is typed to operands only, evaluate() to one level.
     emit[op](load(left), load(right)) assumes both children are leaves. A chain
     makes children arbitrary ExprNodes, so it becomes self.visit(node.left)
     recursing — one uniform visit entry, no leaf/non-leaf split.
  4. parse_expr(tokens, i, end) needs the closing } index before it starts.
     That's the end-delimiter contract; a while peek() loop replaces it, and the
     } is just expect("rbrace", …) after the expression returns.
  5. Argv shape. if len(argv) != 3 (compiler.py:181) hard-codes exactly two
     args. --ast takes one, and must write nothing.
  6. build() both checks and emits, in one pass, keyed by string tags. Split:
     parser raises syntax errors, the walk raises semantic errors.

  3. Three places the practice-2 design will resist

  a) The lexer's brace balancing is a mini-parser inside the lexer. brace_col
  (lexer.py:61, 73-75, 89-96) rejects { inside {, } without {, unclosed { at end
  of line. Harmless this week — the language still has no nesting — but it's
  the front end asserting a grammatical fact, and the handout puts grammatical
  facts in the parser. It'll also bite the moment parentheses arrive. Leave it,
  but note the two positions differ: the lexer reports the brace column, a
  parser would report the offending token's.

  b) parse() identifies statements by tuple tag and grabs statement[1] as "the
  token to blame." Lines 105-111 do statements[i+1][1] for the after-exit error
  and statements[-1][1] for the missing-exit error. That works only because
  every tuple happens to hold a token in slot 1 — decl's name, assign's name,
  exit's exit keyword. It's exactly the "for a statement after exit, blame the
  statement, not the exit" rule in CLAUDE.md, and it's held together by
  positional luck. With ProgramNode(statements, exit) the exit node is
  structurally separate, so the check becomes "did we already have an exit node
  when this line arrived" — and node.line/node.col is uniform. But: ExitNode is
  now the node that blames itself, and DeclNode/AssignNode carry the name's
  position, not the statement's first token. For i32 x{1} after exit, practice 2
  blames column of x; the handout says "the position of the first byte of the
  token that caused the error." Check your existing .expected files — this is a
  silent column change.

  c) "End of line" has no position in the current design. The handout adds a
  specific rule: when a line ends too early (x := x +), report "the column right
  after the last token of that line." Your expect() (compiler.py:22-24) does
  end = tokens[-1] and reports the last token's own column. For x := x + that's
  the column of +, not +'s column plus 1. Every "found end of line" test will
  need its column recomputed — and per CLAUDE.md, by hand.
